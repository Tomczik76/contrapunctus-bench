# Provenance — results/2026-06-10

How the four `*.report.json` files in this directory were produced, where
they came from, and how to reproduce the tables from them. This was the
first release cut with `make release` (the tooling added alongside it);
the carry-vs-rescore decisions below were made by its coverage and parity
gates, not by hand.

## What these files are

Each `*.report.json` is a per-piece **tier-count report** on the
autonomous `single-pick` mode: one row per piece with `total`
(ground-truth events) and the six match-tier counts
([../../methodology/match-tiers.md](../../methodology/match-tiers.md)).
They are the *scored* output, not raw per-event predictions — scoring (the
engine-coupled, normalizer-dependent step) is already baked in, so
aggregating them is pure arithmetic (`harness/score.py`). They were
slimmed to `single-pick` rows only; the source reports also carried
internal per-detector / key-accuracy diagnostic modes that are not part of
this comparison.

`scores.json` and `common_subset.json` are generated by
`harness/score.py` from these four files; do not hand-edit them.

## What was re-scored vs carried forward, and why

**The neural rivals' inference was NOT re-run.** AugmentedNet's annotated
RNtxt outputs and AnalysisGNN's analysis CSVs are the same fixed
artifacts as in the 2026-06-09 release. What changed is the *scoring* of
those fixed outputs: since 2026-06-09 the comparison pipeline was unified
(one shared normalizer and aligned scoring for all four engines) and the
ground-truth parse was corrected on three pieces (repeat-expansion fixes:
Bach Chorales 179 and 359, Brahms "Marias Lob" — +82 events on the same
505-piece subset, 48,155 → 48,237). Carrying the 2026-06-09 rival
reports forward passes the coverage gate (identical piece roster) but
fails the parity gate against the published page — the page re-scores
rival outputs through the current pipeline on every refresh — so the two
neural-rival reports here are the re-scored ones. This moves rival
numbers without any rival re-inference (e.g. AnalysisGNN's Brahms exact
drops 43.09 → 28.57 under aligned scoring, costing it its only genre
win).

**Music21 is carried forward** from 2026-06-09 (generated 2026-06-08):
it is a fixed external tool, its report predates and is unaffected by the
re-score, and the published page uses the same artifact (its numbers
reproduce exactly).

**The engine report was regenerated, not recovered.** The page's numbers
were first published from a run at engine commit `67b26d0b`; that run's
per-piece report was not preserved. This release's report was regenerated
at `4ac65cc6` — later by two commits, whose engine changes are a rename
plus dead-detector deletion (verified behavior-neutral on exact-match).
Every exact-match number reproduces the `67b26d0b` run to the decimal.
Two annotator-defensible (a-d) cells differ by a hair from the numbers
the page briefly published from the `67b26d0b` run (genre-balanced a-d
69.46 → 69.49, Brahms a-d 52.65 → 52.88, ≈2 of 823 Brahms events
re-tiered): the chord-ID fold-model training mass is
environment-dependent (training-only extra pieces are filtered by local
score availability and detected-key agreement), so two near-tie
*wrong-label* picks landed in different defensible tiers. The page data
was regenerated from this same run so that this repo and the site
describe one run, exactly.

## Reproduce the tables

```bash
make score      # or: python3 harness/score.py results/2026-06-10
```

`common_subset.json` pins the 505-piece 4-engine intersection
(48,237 ground-truth events as the engine's parser counts them);
`harness/score.py` fails if a re-run's intersection differs (the coverage
gate — see protocol.md).

## Sync rule

Regenerate this directory whenever the engine repo regenerates
`frontend/src/data/benchmarks.json` (the `make release` path). The two
must always agree — the `/engine` page and this repo describe the same
engine build.
